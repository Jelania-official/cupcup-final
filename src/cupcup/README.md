# Cupcup 复赛独立包

这是复赛正常 2v2 的独立策略包。初赛工程只用于算法和实验结果参考，
本包不从初赛目录读取源码、模型或配置。当前版本优先复用已经有回放和
仿真记录支持的视觉解码、脚位标定和动作队列接口，再在其外层加入复赛角色
和安全逻辑；不复制其他球队的整套机器人代码。

## 启动

```bash
source /opt/ros/humble/setup.bash
source install/setup.bash
ros2 launch cupcup player_launch.py
```

需要先启动当前工程的 `start`、`gamectrl` 和对手策略包。裁判会把
`cupcup_1`、`cupcup_2` 映射到实际的红方或蓝方机器人。

开发时可以在 ASCII 路径构建，避免中文路径影响 `colcon`/`rosidl`：

```bash
colcon build --build-base /tmp/cupcup-build --install-base /tmp/cupcup-install \
  --packages-select cupcup
```

## 角色与比赛策略

`cupcup_1` 默认是主进攻者，`cupcup_2` 默认是防守者，但角色不是永久锁死的。
两台机器人通过现有 `common/msg/Talk` 交换球权声明、球置信度、粗略全局球坐标、
健康状态和行为状态。相近条件下由低编号机器人优先取得球权；前锋拥有球权时，
后卫回到己方球门—球方向的防守锚点；前锋失联、失去球权或球进入己方半场时，
后卫可以临时接管。后卫接管时，前锋移动到支援位置而不是从后方抢球。

这套策略只使用现有图像、IMU、头部、粗定位、`Talk`、`BodyTask` 和 `HeadTask`
接口，没有新增 ROS 消息，也没有把初赛工作区作为运行依赖。

## 运行逻辑

- `INIT/READY/PAUSE/END`、进球后的比分变化和重新开局都会清掉旧球、旧脚法
  和旧状态；重新开球有短暂保护时间。
- YOEO/OpenCV 模型候选阈值沿用初赛回放验证值 `0.30`；四张关键 Webots
  画面的解码误差记录在 `models/bitbots-2026/conversion_validation.json`。
  运行时通过连续多帧确认、时间跟踪和创新门控过滤跳点；没有模型时使用传统
  OpenCV 回退。
- 主进攻流程为 `SEARCH → APPROACH → ORBIT → ALIGN → SETTLE → KICK → VERIFY`；
  后卫接管时复用同一套已标定的接近和踢球闭环，但始终经过后卫中线保护。
- 射门前根据边线风险和稳定的机器人检测选择通道；接近阶段检测到机器人挡路时
  会减速并侧向绕行。
- 后卫在 `HOME/TRACK/CLEAR` 三种防守行为间切换，默认跟踪球门—球的横向方向，
  只有满足多帧稳定条件才执行一次解围，避免重复动作队列。
- 前锋禁区和后卫中线保护带带有滞回，降低粗定位抖动。
- 相机、IMU、头部、定位或裁判链路超时都会停止身体任务；摔倒后的起身仍由
  当前 `motion` 层负责，策略等待站稳后再恢复。

## 已执行的验证

包内有两个不依赖 ROS 的测试：`ball_tracker_test` 和 `strategy_logic_test`；
构建时还通过 `cppcheck`、`flake8`、`lint_cmake` 和 `pep257`。真实 Webots 2v2
回归覆盖了 4 个机器人控制器、裁判消息、模型加载、传感器链、红蓝双方的视觉闭环
和同代码双队自对抗。测试夹具由 `tests/run_match.py` 管理，`unirobot` 是当前工程
的弱模板对手，不代表正式比赛队伍；`--opponent cupcup` 会以 `cupcup` 红方对
`cupcup_b` 蓝方启动两套相同逻辑；`tests/scripted_opponent.py` 只用于可重复的
压力场景。

已获得的历史 Webots 证据包括：事务闩锁版本红方 900 秒完整局运行 911.9 秒，
裁判记录 1 次 `BALL_GOAL`、1 次 `BALL_OUT` 重开，最终比分 `1:0`；前锋 11 次
KICK，0 跌倒，12 次健康等待。动作抢占版本的另一场 480 秒局也得到 `1:0`，
说明进球闭环可重复出现。事务闩锁版本红方 300 秒回归为 3 次 KICK、0:0、0 跌倒，
用于验证重复动作保护。

清理测试残留后，真实蓝方 180 秒回归确认机器人被映射为 `blue_1/blue_2`，结果为
`0:0`、2 次 KICK、0 跌倒；蓝方已经完成看球—接近—踢球闭环，但仍需多个随机种子
验证开局和进攻效率，不能把红方成绩直接外推到蓝方。

最新修复版本的回归为：红方 180 秒实际 191.4 秒、3 次 KICK、0 次跌倒；红方
300 秒实际 314.2 秒、5 次 KICK、0:0、0 次跌倒；蓝方 180 秒实际 199.0 秒、
2 次 KICK、0:0、0 次跌倒。一次修复前的 600 秒随机局曾出现前锋在固定大角度
视线下反复“零前进原地转向”的卡死，未踢球；已改为低速弧线接近后，短局和长局
均重新进入 `ORBIT → ALIGN → SETTLE → KICK`。这次迭代验证的是恢复能力，不把
一次失败局隐藏掉。

红方 `cupcup` 对蓝方 `cupcup_b` 的最新 120 秒自对抗完成双队启动、Talk 仲裁和
红蓝映射，0 次跌倒；该随机局双方未完成 KICK，因此只作为协同安全性回归，不作为
进攻性能结论。历史自对抗局曾出现 6 次 KICK。`unirobot` 仍只是当前工程的弱模板
对手，不代表正式比赛队伍；正式成绩取决于与其他队伍实际比赛。

`rush` 压力夹具已验证测试工具能启动双机器人，但夹具本身会频繁摔倒，导致
cupcup 进入安全等待，不能作为正式对手成绩；正式比赛对手应替换为不带此类
运动学缺陷的真实队伍包或经过校准的对手模型。当前版本已具备动态球权、故障接管、
移动防守锚点、基本避让和红蓝自对抗启动能力，但蓝方长局效率和强对手下的球权
稳定性仍需继续回归。
