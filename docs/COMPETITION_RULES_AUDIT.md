## 结论与依据

比赛是参赛队伍之间的 2v2，不是只需击败 unirobot。规则明确红蓝两队随机分配，
模型存在红蓝色板；此前把“阵营识别尚未实现”说成“平台没有识别依据”，是错误的。
另外，cupcup 前锋保护的基准常数接近小禁区，但规则禁止进入的是**己方大禁区**。
历史“无罚站”和边界单测通过，不能证明这条规则合规。

必须分清三类证据：

1. **规则**：[复赛细则 PDF](<东南大学第二十三届RoboCup竞赛规则 KidSize组(复赛细则） .pdf>)，标注 2026.9。
   内部冲突交由组委会解释，不自行挑选有利版本。

编号的活动范围不随软件“主攻/支援/接管”角色改变：2 号可以在己方半场抢球、
解围、踢球，但不能因为接管进攻就进入对方半场；1 号可以回防，但不能进入己方大禁区。
两张图均注明只是示意图，比例不完全符合实际，不能从图上量出正式坐标。

### 小组赛与晋级

- 20 队分 5 组；每场 15 分钟，胜 3 分、平 1 分、负 0 分。
- 每组前 3 名出线，共 15 队。
- 组内排序：积分、净胜球、胜负关系、**预赛进球数**。
  保留原词，不自行替换成本次小组赛总进球数。
- 五个第四名比较：小组赛积分、净胜球、总进球数、胜场数、初赛排名。
  最好的第四名出线并固定为 16 号种子；共 16 队晋级。
- 第 2 页对阵示意不能单独推出完整 16 队的种子编排。

### 淘汰赛与文档歧义

- 单场淘汰，每场 15 分钟，两两对决至冠军。
- 第 1 页平局“重开一局”，第 2 页平局“加时赛”，均为先进球者胜。
  是否同一重置/计时流程，需确认。
- 加时仍平局：按小组赛积分、净胜球、胜场数、预赛进球数依次晋级。
  加时时长、所有指标仍相同的处理没有规定。
- 第 1 页区分底线球和边线球；第 3 页把足球出界统一描述为中心球、双方边线外。
  不能擅自认定其中一页覆盖另一页。
- 第 3 页出界条款后有缺少主语的罚站句。不能据此推导“球出界就罚所有机器人”。

## 二、阵营识别与信息权限

### 有识别依据，不等于已完成识别

PDF 明确红蓝随机分配；模板通过 `gamectrl/get_color` 按队名取得己方颜色。
[world](../src/simulation/webots/models/worlds/sim-robot.wbt) 配红色 `0.8 0 0`、
蓝色 `0 0 0.8`，并有 1、2 号纹理；
[机器人 PROTO](../src/simulation/webots/models/protos/SEURobot.proto) 将颜色用于
`FrontCover` 和 `BackCover`，并非全身染色。

cupcup 已支持每帧最多四个机器人框、红蓝色板分类和短时局部关联；其漏检、遮挡、
位置精度与持续身份尚未完成充分验证，不能将候选当作精确对手地图。
颜色、号码、跨帧身份是三个不同问题；色板或号码被遮挡时应保留未知，
不能根据所在半场强行判敌我。光照鲁棒性要实测，不能承诺每个视角都能识别。

### 文档许可与技术可访问性

| 接口 | 文档 / 模板依据 | 判断 |
| --- | --- | --- |
| 自机图像 | OpenCV Mat，RGB 三通道 | 可用；不能直接按 BGR 处理 |
| 自机 IMU | 朝向 yaw，方向需自行测试 | 可用；结合消息定义与实测校准方向和单位 |
| 自机头部角 | 文档称 yaw/pitch 关节角；原控制器直接发布下发目标，而非编码器实测值 | 可用但有动作跟随误差；不能当同步的真实相机姿态 |
| 自机粗定位 | Location x/z，精度一米；模板订阅自机 | 可用但不是真值 |
| 比赛数据 | “允许调用”列表为 red_score、blue_score、state、mode | 这些有明确文档依据 |
| 队内通信 | Talk，仅限复赛，收队友、发自身 | 可分享各自允许获取的观测 |
| 己方颜色 | 模板 GetColor 服务 | 应获取而不是硬编码 |
| 身体/头部控制 | BodyTask / HeadTask | 正式执行通路，不是测试端直接改坐标 |
| 对手/队友 Location | Supervisor 发布四台位置，模板只演示自机订阅 | **未证实允许直接读取其他机器人的定位**；保守方案是队友 Talk、对手视觉 |
| GameData 额外字段 | 消息含 remain_time、second_time、双方球员状态，但许可列表未列 | **需确认策略的读取权限** |
| FieldData、Supervisor 真值 | 用于当前裁判/测试，FieldData 本身也无球坐标 | 未找到策略消费许可；仅放测试端 |
| 其他机器人图像/IMU/跨队通信 | 话题可能技术可见，文档未授权 | 不据“能订阅”推定允许使用 |

`motion` 和 cupcup 当前均使用己方球员状态停止罚站机器人；基础设施依赖此字段，
但不能代替对策略权限的正式澄清，也不应未确认就删除罚站停止保护。
复核原 ZIP 后确认：原 motion 本身就有这一罚站停止逻辑，不是本队新增的权限假设。

原图像时间戳/IMU stamp 使用默认零时间；HeadAngles 的 time 未赋有效采样时间；
Location 原来只有 x/z。我们后来加的 Location stamp、统一仿真时间和颈部传感器反馈，
都不是发布基线提供的能力。正式包应能处理原输入，或先获得修改环境的明确许可。

BodyTask：`step/lateral` 为米，正数向前/向左；`turn` 为度，正数左转；`count` 为步数，
通常取 2。动作名 `left_kick`、`right_kick`、`ready`；HeadTask 的 mode 目前未使用。
消息有点球模式，但本份复赛细则规定正常 2v2，没有新增点球赛制。

## 三、场地几何与当前实现差异

以下是**改动前 ZIP 的模型/活动裁判事实**，不是 PDF 给出的精确尺寸。
已经逐字节确认：模型、GUI 与首次基础设施提交相同；正常 Supervisor 与该提交相同。
因此下述禁区、球半径、初始摆位及计时差异在原包中就存在，不是本队日志修改造成的。
场地中心为原点，x 沿球门方向、z 沿场地宽度；当前 red 己方在 +x，blue 在 −x。

| 项目 | 当前参数 / 判定 | 含义 |
| --- | --- | --- |
| 场地 | 9×6 m，x=±4.5、z=±3，线宽 5 cm | RobocupSoccerField 的 KidSize 参数 |
| 球门 | 内宽 2.6 m，高 1.2 m | RobocupGoal 的 KidSize 参数 |
| 大禁区 | 深 2 m、宽 5 m；忽略线宽时，己方纵向约 2.5～4.5 m、横向 ±2.5 m | J=2、K=5，经中心偏移/world 旋转得到 |
| 小禁区 | 深 1 m、宽 3 m；纵向约 3.5～4.5 m、横向 ±1.5 m | E=1、F=3，不能当大禁区 |
| cupcup 前锋保护 | 2026-10-07 已从 3.55/1.45 修正为大禁区 2.5/2.5，并扩张定位缓冲 | 本队保护，不修改原裁判；定位误差下仍需轨迹验证 |
| 裁判前锋判罚 | red：x>2.70 且 abs(z)<2.00；blue 镜像 | 活动 StopX/StopZ；与大禁区标线也不一致 |
| 裁判后卫判罚 | red：x<−0.20；blue：x>0.20 | 不是文字中线 x=0；身体/中心判定需确认 |
| 裁判机器人出界 | 中心 abs(x)>4.75 或 abs(z)>3.25 | 加了代码中的球/机器人半径，不是场线本身 |
| 球半径 | world 0.07 m，裁判常量 0.05 m | 视觉与判罚几何存在差异 |
| 裁判进球 | abs(z)<1.35、球中心过 x=±4.55；−x 红得分、+x 蓝得分 | 不检查球高度，有 10 墙钟秒得分防抖 |

Supervisor 中未用于活动检查的 `forbidAreaX=3.55`、`forbidAreaZ=1.45`，
不构成“大禁区官方定义”；BoundaryGuard 原注释中的 intended dimensions 不能再当依据。
按用户确定的原则，运行判定以组委会原包活动裁判为基准，不自行改裁判配合本队；
文档写的是大禁区，不能把原包较小判罚范围改写成文档规则。
当前可采用的保守设计是：地图分别显示大禁区标线和裁判判罚区域，保护按二者并集及
定位不确定范围规划；后卫以文档中线 x=0 保护，不利用裁判的 0.2 m 容忍越线。
确认此 ZIP 来源后即可据它锁定执行基线，不必再把所有已查清代码行为笼统列为未知。

### 重开和罚站

- 当前 INIT 中心坐标：red_1 `(1.5,-3)`、red_2 `(2.3,3)`；blue 的 x 镜像。
  z 在场线上；是否符合“边线外”及身体判定，需确认。
- 当前进球重开由 1 号在中圈附近/边线，2 号在己方点球点（x=±3、z=0）。
  这是代码安排，图 2 本身未指定号码。
- 当前罚站位置复用初始位置，2 号 x=±2.3，不完全等同于“靠近中线”。
- 出边线后 Supervisor 立即球回中心、机器人在中场/球门前；GUI 收事件进入 PAUSE。
  若随后人工 INIT，又按初始边线位置摆放；完整重开链不一定保留边线特定站位。
- 底线出界、进球、100 秒不动使 GUI 暂停，由操作员 INIT/READY/PLAY。
  GUI 不自动执行淘汰赛加时和完整赛程。
- INIT 清除罚站状态；重开是否应保留罚站，PDF 未说明。

## 四、时间与测试结果的适用范围

系统墙钟、Webots 仿真时间、裁判累计 PLAY 时间不同。PDF 未定义它们的对应关系。

- GUI 以 20 ms Qt 回调在 PLAY 累加、递减 900 秒，不直接读取 Webots 时间，
  也不是严谨的连续墙钟计时，会受事件循环负载影响。
- GUI 罚站按比赛剩余时间差，暂停不推进，释放条件是大于 30，可能超过 30 秒。
- Supervisor 球不动按 PLAY 中 20 ms 仿真步数计数，分量约 1 cm 的变化才算移动。
- 进球防重复使用系统时间，事件时钟并不统一。
- `mock_gamectrl.py` 按启动墙钟扣 900 秒，包含初始准备/重开；罚站按墙钟；
  重开按 2/4/6 秒自动切换，剩余时间为零也不自动发布 END。不能称正式裁判等价实现。
- `run_match.py --duration 900` 是墙钟参数；单独 900 墙钟秒或 900 仿真秒都不足以
  证明按正式裁判完成十五分钟。应记录三类时间、状态变化，并确认最终比赛口径。

历史比分、跌倒、触球和健康日志仍可作实验数据，不能据此宣称：完整规则已验证、
前锋大禁区合规、正式十五分钟验收完成。

## 五、需组委会确认的问题

原包已经明确执行阈值、摆位和计时实现；不再将这些归为“源码未找到”。
剩余是原包来源确认、文档与源码冲突及文档没有授权的事项：

1. **来源与禁区差异**：请用户确认找到的 ZIP 是组委会发的原包；原裁判按中心点和
   上表阈值判罚已明确，但其范围与大禁区标线不同，是否另有更正仍需官方说明。
2. **边线重开**：第 1 页中场/球门前与第 3 页边线外哪项为准？实际 PAUSE→INIT
   是否覆盖特定站位？开场、进球、边线球和罚站的精确位置/编号如何安排？
3. **加时**：重开与加时的初始化/计时流程、加时时长，以及所有晋级指标相同的处理。
4. **时钟与罚站**：原 GUI 仅计 PLAY、区域违规同样走罚站、Init 清罚站已查明；
   这些与文档时长是否有补充口径、申请 Init 的人工流程，源码不能代替官方解释。
5. **数据权限**：其他机器人 Location、GameData 时间与双方球员状态、FieldData
   是否可被策略读取。话题可见不等于允许使用。
6. **提交与开源边界**：是否只交球队包；能否修改 common 消息、运动控制器/机器人
   模型；开源代码与预训练权重如何合规引用。当前模型 provenance 仍注明许可待核实。

## 六、下一步开发约束（本队建议，不是比赛规定）

1. 确认并保留原 ZIP、指纹及组委会补充答复，不把本队首次提交当基线，不微调裁判过关。
2. 统一场地几何/输入权限，修正前锋大禁区保护；边界场景测合规，不靠短局未罚站推断。
3. 感知先用自机图像/IMU/头部/粗定位和队内 Talk，利用已有红蓝依据验证身份与几何，
   明确遮挡/未知状态，不先堆复杂战术。
4. 可视化区分“机器人实际获知”与“测试真值”；二维全信息模式只作研究，
   不向实际比赛策略偷渡全信息。
5. 按用户当前方向先验证地图的信息质量、可视化与记录，不要求每次感知改动测进球。
   正式口径明确后再校准比赛夹具、做比赛级验收。
